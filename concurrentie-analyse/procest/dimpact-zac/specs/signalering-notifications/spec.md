# Signalering (Notifications) -- Dimpact ZAC

## Purpose
Competitive analysis spec documenting how Dimpact ZAC implements its notification/signaling system.
- **Product**: Dimpact ZAC
- **Category**: Notifications & Alerts
- **Relevance to Procest**: Notifications keep users informed about case and task changes

## Architecture Overview
Signaleringen are stored in a local PostgreSQL table and delivered through two channels: in-app (WebSocket) and email. The system tracks which notifications have been sent to avoid duplicates.

Key services:
- `SignaleringService` -- core notification CRUD and delivery
- `SignaleringRestService` -- REST endpoint at `/rest/signaleringen`
- `SignaleringMailHelper` -- email template resolution
- `SignaleringEventUtil` -- event creation utilities

## Data Model

### Signalering Entity (JPA)
| Field | Type | Description |
|-------|------|-------------|
| id | Long | Auto-generated ID |
| type | SignaleringType | Event type reference |
| tijdstip | ZonedDateTime | Timestamp |
| targettype | SignaleringTarget | USER or GROUP |
| target | String | User ID or group ID |
| subjecttype | SignaleringSubject | ZAAK, TAAK, or DOCUMENT |
| subject | String | Entity UUID |
| detail | String | Additional detail (e.g., document UUID for ZAAK_DOCUMENT_TOEGEVOEGD) |

### SignaleringType.Type (enum)
- `ZAAK_OP_NAAM` -- case assigned to user
- `ZAAK_DOCUMENT_TOEGEVOEGD` -- document added to case
- `TAAK_OP_NAAM` -- task assigned to user

### SignaleringTarget
- `USER` -- individual user
- `GROUP` -- organizational group

### SignaleringSubject
- `ZAAK` -- case
- `TAAK` -- task
- `DOCUMENT` -- document

### SignaleringInstellingen (Settings)
Per-user or per-group configuration of which notification types are enabled and through which channels (in-app, email).

### SignaleringVerzonden (Sent Tracking)
Tracks which notifications have been sent via email to prevent duplicates.

## Business Logic

### Notification Creation
1. Event occurs (assignment, document addition)
2. `SignaleringEventUtil.event()` creates a Signalering
3. `isNecessary()` check: groups always notified, users only if not the actor
4. If existing notification found for same type/target/subject: update timestamp
5. Otherwise: persist new notification
6. Send WebSocket screen event `SIGNALERINGEN.updated`

### Email Delivery
1. Check if target has email enabled for this type in settings
2. Resolve mail template for the notification type
3. Build bronnen (data sources) based on subject type:
   - ZAAK: load zaak, optionally document for ZAAK_DOCUMENT_TOEGEVOEGD
   - TAAK: load task + parent zaak
   - DOCUMENT: load document
4. Send email via MailService
5. Record SignaleringVerzonden to prevent re-sending

### Notification Deletion
- Viewing a case/task auto-deletes related notifications for that user
- Scheduled cleanup deletes notifications older than N days
- Batch delete by parameters with grouped screen events

### Dashboard Integration
- Notifications feed into dashboard cards
- Paginated listing: `listZakenSignaleringenPage`, `listTakenSignaleringenPage`
- Count endpoints for badge numbers

## Requirements (as observed)

1. Three notification types covering the main user-relevant events
2. Self-actions do not generate notifications (isNecessary check)
3. Duplicate notifications update the timestamp rather than creating new records
4. Two delivery channels: in-app (WebSocket) and email
5. Per-user/group granular settings for each notification type
6. Automatic cleanup of old notifications
7. Viewing an entity auto-dismisses its notifications

## User-Facing Alert Types (from User Manual)

The user manual describes broader alert types beyond the 3 code-level types:
- Document additions to user's cases
- Case assignment notifications
- **Deadline approach warnings** (both target date and fatal date)
- Task assignments
- **Task deadline alerts**

Note: Deadline-based signaleringen are generated by Kubernetes cron jobs (daily), not by the event system.

### Delivery Methods
- Dashboard widget display (cards)
- Email delivery (user-configurable per type)
- Red indicator on home button for new alerts
- Daily cron job "Send signaleringen" for deadline-based alerts
- Daily cron job "Delete old signaleringen" for cleanup

## Comparison Notes
- ZAC's notification system is focused (3 event types + deadline cron jobs). Procest could start similarly simple.
- The "self-action suppression" pattern is important for UX
- The sent-tracking (SignaleringVerzonden) prevents email spam -- good pattern
- Auto-dismissal on view is a nice UX touch
- WebSocket delivery provides real-time updates
- Deadline alerting via cron jobs is a pragmatic approach -- runs daily rather than real-time
- User-configurable email preferences per notification type is essential for adoption
