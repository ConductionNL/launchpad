# CaseFabric CMMN Modeling Documentation

**Source:** https://guide.cafienne.io/docs/cmmn/overview, case-plan, case-file, case-team

## CMMN Overview

CaseFabric implements CMMN 1.1 (Case Management Model and Notation), published December 2016 by the Object Management Group (OMG). CMMN provides a graphical language with explicit semantics for describing case lifecycles.

## Three Core Elements of a CMMN Case

### 1. Case File

The Case File holds all data relevant to the case. It is the central data container.

- Each case instance has a **single Case File**
- Case workers can add, remove, and modify data without executing a task (if authorized)
- Contains **Case File Items** (any data type: database values, documents, spreadsheets, media)
- Case File Items have a **Definition** that defines structure and properties
- In CaseFabric, Case File Items map to JSON object structures
- Hierarchical organization via containment (parent/child)
- Case File Item Properties have name and type (mapped as object attributes)

**Case File Item Lifecycle:**
- States: Available, Discarded
- Transitions: create, update, replace, delete, add child, remove child
- Note: CaseFabric does NOT support Case File Item references

### 2. Case Plan

The Case Plan describes the lifecycle of the case. It contains:

**Plan Items:**
- **Stages** - Group related plan items; contain other stages, tasks, milestones
- **Human Tasks** - Require user action; need a performer role
- **Process Tasks** - Execute external processes or services (e.g., HTTP calls)
- **Case Tasks** - Execute sub-cases (standalone or child of current case)
- **Decision Tasks** - Invoke decisions
- **Milestones** - Achievable targets showing case progress
- **Timer Event Listeners** - React to elapsed time
- **User Event Listeners** - React to user-triggered events (restricted by role)

**Sentries (Entry/Exit Criteria):**
- Guards that watch for events of interest
- Entry criteria: conditions for a plan item to start (transition from Available)
- Exit criteria: conditions for a plan item or stage to complete
- Events can come from Case Plan or Case File
- When multiple entry/exit criteria exist, only ONE needs to be satisfied
- Evaluated when events arrive or are generated by the system

**Plan Item Properties (Behavioral Rules):**
- **Repeat** - Conditions under which a plan item repeats (new instance per repetition)
- **Required** - Must complete/terminate before containing stage/case can complete
- **ManualActivation** - Whether user must manually activate the item
- **Applicability** - Rules for discretionary items
- **Stage.autocomplete** - Auto-complete stage when all required items complete

### 3. Case Team

- Case roles authorize workers to perform tasks, plan, and raise events
- Each case has its own team (same person can have different roles in different cases)
- Roles are assigned via the Case Designer
- Performer role on Human Tasks restricts who can work on them
- Authorized roles on Discretionary Items and User Events

## Case Lifecycle States

```
[Created] --> Active --> Completed --> Closed
                    \--> Terminated --> Closed
                    \--> Failed --> Closed
                    \--> Suspended --> Active (re-activate)
```

## Plan Item Lifecycle States

```
[null] --create--> Available --start--> Active --complete--> Completed
                           \--enable--> Enabled
                                       Active --terminate--> Terminated
                                       Active --suspend--> Suspended
                                       Active --fault--> Failed
                                       Suspended --resume--> Active
```

Plan item responses include: `historyState`, `currentState`, `transition`.

## Task Implementation

- Human Tasks: reference a HumanTask Model (input/output parameters + UI rendering)
- Process Tasks: reference a Process (with URI for real implementation)
- HTTP calls configured via extension elements in CMMN XML
- Case Tasks: reference another case definition (hierarchical decomposition)

## Expression Language

CaseFabric uses **Spring Expression Language (SpEL)** for:
- Sentry conditions (entry/exit criteria)
- Repetition rules
- Required rules
- Due date calculations
- Dynamic task assignment
- Operates over Case File Items
- Also supports constants and time-based expressions

## Discretionary Items

- Available to case workers at their discretion (vs. planned items)
- Can be added by case workers acting as "case engine"
- Controlled by Applicability Rules
- Authorization via roles
